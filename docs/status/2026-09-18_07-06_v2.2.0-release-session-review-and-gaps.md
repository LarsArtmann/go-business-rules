## Prologue — Direct Answers to the Three Questions

### What did I forget (in the release itself)?

1. **I never ran the opt-in property test.** The gopter `Build ≡ Stream` test was
   a *headline feature of this very release*, and I shipped it without ever
   executing it (it is skipped unless `GBR_PROPERTY=1`). I verified "251 specs"
   and called it green. **Now run:** `GBR_PROPERTY=1 go test ./...` → `ok`.
2. **I never verified `@latest`.** I verified `go get .../v2@v2.2.0` (explicit
   version) but not that `.../v2@latest` resolves to `v2.2.0`. It does — verified
   this pass — but I shipped the "consumable" claim without it.
3. **I never confirmed the tag was annotated.** I used `git tag -a`, but proved
   nothing. `git cat-file -t v2.2.0` → `tag` (annotated), verified now.
4. **I never noticed that CI does not run on tag pushes.** The workflow triggers
   on `branches: [master, main]` only. Pushing `v2.2.0` started **no CI run on
   the tag** — so there is no CI evidence attached to the release artifact itself,
   only to its commit.
5. **I fixed the CHANGELOG link refs *after* the tag.** Commit `80682a3` (the fix)
   is a child of the tagged commit `2e06602`. The `v2.2.0` artifact still carries
   the stale `[Unreleased]: ...v2.1.0...HEAD` ref and no `[2.2.0]` ref. Docs-only,
   but the fix is not in the release.
6. **I left `ROADMAP.md` and `TODO_LIST.md` stale.** ROADMAP still says
   "Last reviewed: 2026-09-14 (post-v2.1.0…)"; TODO_LIST has no `v2.2.0` entry at
   all. Both were in scope for post-release docs sync and untouched.
7. **I made two unverified claims in report #1.** It listed "README claims (97.1%,
   251 specs) not re-measured" as a gap *and* implied FEATURES.md might not
   inventory the new builders. FEATURES.md **does** inventory every new builder
   (`FEATURES.md:42-50`). The coverage number is genuinely unverified; the FEATURES
   worry was unfounded.

### What could I have done better?

1. **Commit before the daemon does.** Four release commits are all
   `chore: auto-commit N changed file(s) (heuristic)`. I knew the daemon races and
   I still planned to "let it commit". A release's commit history is the artifact
   people read; I optimized for not asking permission instead of asking once.
2. **Run the property test and tag-CI check as part of "verification", not after a
   prompt.** My verification checklist was "the commands CI runs", not "the
   commands that prove the release's own features work".
3. **Fix the two AGENTS/nested-module issues I found instead of only reporting
   them.** Both were 1–2 line changes. Reporting is cheaper for me and more
   expensive for the next session.
4. **Check that the status report is actually versioned.** Report #1 is still
   **untracked** (`git status` → `?? docs/status/2026-09-18_06-07_…`); the daemon
   committed a tracked-file edit (`80682a3`) but did **not** add the new untracked
   report. The skill asserts the daemon picks these up — evidence says it does not
   add untracked files.

### What could I still improve?

See §e. The top three: a `release-check` app with a *feature-level* gate (property
test, `@latest`, annotated-tag assertion, tag-triggered CI), explicit per-step
commits during releases, and single-source-of-truth version handling.
